# 플레이어 경험 게이트 계약

이 문서는 기능의 정확성과 결정성을 검증하는 capability gate 옆에, 그 기능이 플레이어에게 이해 가능하고 수정 가능한 경험으로 이어지는지를 검증하는 experience gate를 둔다.

Experience gate는 자동 테스트를 대체하지 않는다. 동일한 seed·명령·상태에서 같은 결과가 나오는지를 먼저 증명하고, 그 결과를 플레이어가 관찰하고 대응할 수 있는지를 별도 시나리오로 확인한다.

## 1. 두 종류의 게이트

### Capability gate

- 상태와 규칙의 불변식
- 결정성 checksum과 저장 왕복
- command/query 및 계층 경계
- 성능·메모리·플랫폼 재현성

### Experience gate

- 플레이어가 현재 상태와 문제를 공개 UI에서 구분한다.
- 문제 원인이 simulation query에서 나온 설명과 일치한다.
- 플레이어 명령으로 원인을 바꾸면 정해진 기간 뒤 결과가 회복되거나 달라진다.
- 같은 목표를 달성하는 배치나 운영 방식이 하나의 정답으로 불필요하게 수렴하지 않는다.
- 검증 시점에 아직 구현되지 않은 후속 시스템을 성공 조건으로 요구하지 않는다.

## 2. 경험 증거

Experience gate는 자동화 가능한 PlayMode test와 고정 시나리오를 우선하되, 사용성 판단이 필요한 항목은 구조화된 수동 smoke로 남길 수 있다. 각 증거에는 다음을 기록한다.

- 사용한 build/commit, OS, Unity 버전
- seed, command log 또는 정확한 재현 단계
- 시작 상태와 플레이어에게 표시된 원인
- 수행한 플레이어 명령
- 결과가 반영된 simulation 기간과 전후 수치
- 통과/실패 판단 및 알려진 문제

단순히 화면이 존재하거나 30분 동안 crash가 없었다는 사실만으로 experience gate를 통과하지 않는다.

## 3. 설명 가능성

- Simulation/Application query가 reason code, factor, 기간을 소유한다.
- UI는 factor를 다시 계산하거나 추측하지 않는다.
- 여러 원인은 결정적인 우선순위로 정렬하고, UI는 상위 원인과 전체 상세 보기로 연결한다.
- 도시 전체 시장 압력과 개별 필지의 개발 실행 가능성을 별도 개념으로 표시한다.
- 값이 지난 기간의 snapshot이면 UI가 그 기간을 구분할 수 있어야 한다.
- Debug inspector만으로 확인되는 정보는 플레이어 대상 experience gate의 증거가 아니다.

## 4. 단계별 최소 경험

| Phase | 최소 경험 계약 |
|---|---|
| P0–P1 | 기반 단계다. 별도 제품성 판단 대신 입력·카메라·셀 선택이 예측 가능하게 동작하는지만 확인한다. |
| P2 | 설치·취소·철거가 가능하고, 고립 도로망과 개발 불가 필지의 이유를 화면에서 구분한다. |
| P3 | 성장 정지 원인을 공개 UI에서 확인하고, 전력 또는 외부 연결을 복구하면 정해진 다음 기간에 성장이 재개된다. 서로 다른 두 도로 배치가 기본 성장 루프를 완주한다. |
| P4 | 빈 신규 도시가 공개 명령만으로 첫 인구까지 도달하며, 저장 전후 공개 원인, 실행 가능한 명령, 다음 기간 결과가 의미상 동일하다. |
| P5 | 혼잡 병목과 도달 불가 원인을 확인하고 철거 없는 도로 변경 또는 버스 투자로 시나리오를 개선한다. 도로 중심과 버스 중심 전략은 모두 실행 가능하고, 표시 차량 수는 설명과 결과를 바꾸지 않는다. |
| P6 | 쇠퇴의 상위 원인을 두 채널 이상에서 확인하고 조건 회복 뒤 재개발까지 추적한다. |
| P7 | 서비스 예산·용량·밀도 조건의 trade-off를 설명하고, 일반/특성화 도시와 정책 유무 지구가 서로 다른 실행 가능한 운영 방식을 제공한다. |
| P8 | 목표 규모에서도 문제 식별과 명령 feedback이 성능 저하 때문에 실질적으로 막히지 않으며, 고정 맵 경계 또는 다음 확장 목표가 명확하다. |
| P9 | 신규 사용자가 첫 15분 안에 핵심 루프와 대표적인 실패 회복을 완료하고, 건물 성장·도로 계층·지구가 도시 외형에서 구분되며 접근성 대체 표현을 사용할 수 있다. |

## 5. P3 접근성 근사

P5 교통 전에는 OD 통행, 혼잡, 차선, 경로 배분을 구현하지 않는다. 대신 도로 그래프에서 외부 연결까지의 결정적 정수 거리인 `NetworkDistanceToExternalGate`를 계산한다.

- 도달 불가는 개발 자격을 막는다.
- 도달 가능한 필지는 거리 band를 진단 factor로 제공한다.
- 용도별 definition은 이 factor에 서로 다른 약한 가중치를 둘 수 있다.
- 접근성 하나만으로 개발 여부나 definition 선택을 결정하지 않는다.
- P5 도입 뒤 같은 query 계약을 실제 통근시간·시장 접근성으로 확장하거나 교체할 수 있어야 한다.

이 근사는 "위치가 전혀 중요하지 않은 MVP"를 피하기 위한 것이며 임시 교통 시뮬레이션이 아니다.

## 6. 데이터맵 공통 UX

데이터맵은 별도 후반 기능이 아니라 각 simulation capability를 플레이어 경험으로 완성하는 진단 채널이다. 존재하지 않는 후속 시스템의 빈 데이터맵을 먼저 만들지는 않으며, 각 Phase에서 해당 query가 준비될 때 함께 추가한다.

- 모든 데이터맵 값, reason, 적용 기간은 Application query/read model이 소유한다.
- 같은 종류의 낮음/높음, 정상/경고/실패는 가능한 한 공통 범례와 방향을 사용한다.
- 색상만으로 상태를 구분하지 않고 icon, pattern, text 중 하나 이상의 대체 표현을 제공한다.
- 지도 선택에서 상세 원인 패널로, 상세 패널에서 원인 위치로 이동할 수 있어야 한다.
- 현재값, 지난 기간 snapshot, preview를 같은 값처럼 섞어 표시하지 않는다.
- overlay가 꺼져 있거나 카메라 밖이어도 simulation 결과는 같아야 한다.
- 데이터맵의 screenshot 존재만으로 통과하지 않고 표시값과 query fixture의 일치를 자동 또는 수동 증거로 남긴다.

## 7. 공간적 도시 저작성

OpenSimCity는 기능 수로 대형 도시 게임과 경쟁하지 않고, 작은 범위에서 플레이어의 배치·운영 선택이 공간과 결과에 드러나는지를 검증한다.

- 동일한 seed와 목표에서도 도로 계층, 교통 투자, 지구 정책, 특성화 선택이 하나의 정답 배치로 수렴하지 않아야 한다.
- 서로 다른 두 계획은 외형만 다른 것이 아니라 유지비·혼잡·접근성·오염·서비스 중 둘 이상의 관찰 가능한 차이를 가져야 한다.
- 반대로 같은 simulation state에 임의의 외형만 붙여 서로 다른 도시라고 판정하지 않는다.
- 경험 증거에는 전체 도시 화면, 주요 데이터맵, 같은 기간의 핵심 지표를 함께 남긴다.
- 생산 에셋 수를 늘리기 전에 placeholder와 palette/모듈 변형으로 이 차이가 읽히는지 먼저 검증한다.

## 8. 마일스톤·해금 안전 규칙

마일스톤은 미완성 시스템을 숨기거나 플레이 시간을 늘리는 수단이 아니라 검증된 기능을 이해 가능한 순서로 소개하는 장치다.

- P3~P7 capability와 P9 onboarding evidence가 준비되기 전에는 필수 Phase 이슈로 승격하지 않는다.
- 데이터맵, 원인 설명, 철거, 기본 복구 수단은 해금 대상으로 두지 않는다.
- 조건은 공개된 값과 기간으로 설명 가능해야 하며 `교통 문제 해결` 같은 불투명한 판정을 단독으로 사용하지 않는다.
- 첫 수직 슬라이스는 영구 양자택일보다 해금 순서 선택을 우선한다.
- 상세 진입 조건은 [Post-MVP 후보와 진입 조건](../Roadmap/POST_MVP.md)을 따른다.
