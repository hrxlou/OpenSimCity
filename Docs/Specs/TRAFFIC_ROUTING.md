# Traffic Routing and Congestion Contract

This document records the P5-02 aggregate traffic-routing contract implemented by
`OpenSimCity.Simulation.Traffic`. It is a derived Simulation result: presentation
systems may observe it through `TrafficRoutingReadModel`, but must not write traffic
volume back into Simulation.

## Source and execution order

The monthly application order is:

```text
Population / employment
Urban economy and market
Growth / development
Trip demand
Traffic routing and edge aggregation
Municipal finance
```

`TrafficRoutingSystem.RunMonth(month)` requires `TripDemandSystem` to have completed
the same month. Repeated or out-of-order monthly runs fail explicitly.

## Units

- OD and edge volume: abstract aggregate trip units per simulation month.
- Road capacity: aggregate trip units per simulation month.
- Free-flow and effective speed: road cells per hour.
- Edge and route travel time: integer seconds.
- Volume/capacity ratio: permille.

All routing and congestion calculations use integer arithmetic. Edge travel seconds
use ceiling division so a positive edge never has zero travel time.

## Road edge and path ordering

A road edge is an undirected cardinal pair of adjacent cells. `RoadEdgeKey` stores its
endpoints in the project `CellCoord` order, so aggregation never depends on insertion
or hash-table iteration order.

The shortest-path queue is ordered by:

1. cumulative integer travel seconds;
2. row-major road-cell index.

When complete routes have equal travel time, their complete `CellCoord` sequences are
compared lexicographically. This rule determines representative route order and the
deterministic remainder allocation when an OD amount is split across routes.

## Representative routes

Each reachable OD pair returns one to three representative routes. The first route is
the deterministic shortest route. Additional alternatives are generated by excluding
one edge from an accepted route, rejecting duplicates, and sorting candidates by the
same travel-time and full-sequence rule.

A matched OD amount is split evenly across the available routes. Any remainder is
assigned from the first route onward. Route assignment amounts must sum exactly to the
matched OD amount.

## Edge volume and congestion

Every assigned trip unit is added to every canonical edge on its route. For an edge
connecting two road definitions:

```text
capacity = min(endpoint road capacities)
freeFlowSpeed = min(endpoint free-flow speeds)
volumeCapacityPermille = volume * 1000 / capacity
```

At or below capacity:

```text
effectiveSpeed = freeFlowSpeed
```

Above capacity:

```text
effectiveSpeed = max(1, freeFlowSpeed * capacity / volume)
```

The rule is monotonic, integer-only, and deliberately small enough to be replaced by
a separately specified congestion curve later without changing OD or route identity
contracts.

## Unrouted matched demand

A trip-demand row can be matched at the destination-allocation layer but become
unroutable after a road edit. The routing layer retains the amount with one explicit
reason:

- `OriginRoadMissing`
- `DestinationRoadMissing`
- `DifferentRoadComponent`
- `NoPath`

The invariant is:

```text
input matched amount = routed amount + unrouted amount
```

## Cache invalidation

`DeterministicRoutePlanner` caches successful OD route sets by road endpoint pair.
The cache observes `RoadNetworkState.Version` and `RoadConnectivityGraph.DirtyCells`.
A road-version change invalidates route sets in affected components while retaining
entries in unrelated components. The cache is a performance detail and never part of
the deterministic checksum or snapshot.

## Persistence boundary

Traffic route assignments, edge volume, congestion values, and route caches are not
stored in snapshot schema v1. After restore, `TrafficRoutingReadModel` rebuilds the
same derived state from:

- road cells and definitions;
- connectivity graph;
- restored building/economy state;
- rebuilt trip-demand rows.

The routing checksum excludes internal source-version counters, allowing equivalent
restored source state to produce the same checksum even when cache rebuild counts
differ.

## Presentation boundary

UI, congestion overlays, inspectors, and pooled vehicle sampling consume only
`TrafficRoutingReadModel`. They must not enumerate private Simulation storage, mutate
route rows, or feed sampled vehicle counts back into edge volume. This boundary is the
input contract for P5-03 vehicle views and congestion datamaps.
