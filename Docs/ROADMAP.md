# 단계별 개발 로드맵

## 1. 로드맵 원칙

각 Phase는 플레이 가능한 수직 슬라이스와 자동 검증을 함께 만든다. 다음 Phase는 이전 Phase의 완료 조건을 통과한 뒤 시작한다. 아트가 준비되지 않아도 프리미티브와 색상으로 기능을 검증한다.

## 2. 의존 관계

```text
P0 저장소/Unity 기반
  -> P1 그리드·카메라·선택
    -> P2 도로·구역·필지
      -> P3 전력·RCI·성장·경제  [첫 플레이 가능 MVP]
        -> P4 저장·불러오기
          -> P5 집계 교통
            -> P6 토지가치·오염·쇠퇴
              -> P7 공공서비스·밀도
                -> P8 규모 확장·최적화
                  -> P9 아트·UX·출시 준비
```

저장/불러오기는 복잡한 교통과 서비스보다 먼저 구현한다. 이 시점에 런타임 상태와 Unity 표현의 분리가 실제로 지켜졌는지 검증할 수 있다.

## 3. Phase 0 — 저장소와 Unity 기반

### 산출물

- Unity 6 URP 프로젝트 및 고정된 에디터 버전
- Input System, Test Framework, 필요한 URP 설정
- asmdef와 기본 디렉터리
- Bootstrap, CityPrototype, Benchmark Scene 생성 도구
- `.gitignore`, Git LFS, 텍스트 직렬화, Visible Meta Files 설정
- 기본 디렉터리 생성 스크립트 실행
- macOS와 Windows에서 동일 프로젝트 열기 검증

### 완료 조건

- 새 clone에서 문서대로 프로젝트를 열 수 있다.
- Console 컴파일 오류와 누락 참조가 없다.
- EditMode/PlayMode 샘플 테스트가 양쪽 기기에서 통과한다.
- Scene과 Prefab 생성이 수동 배치가 아니라 Editor 메뉴로 재현된다.

### 세부 이슈

- [P0-03: Windows CI baseline and standalone build](Roadmap/P0/P0-03-windows-ci.md)

## 4. Phase 1 — 그리드 상호작용

### 산출물

- `SimulationClock`, `SimulationTick`, `SimulationDate`, `WorldState`, `GridCell`, 청크 인덱스
- 명령 tick/sequence, 시스템별 결정적 RNG와 안정 순회 규칙
- 월드/셀 좌표 변환과 범위 검사
- 제한형 아이소메트릭 카메라 이동·줌·90도 회전
- 포인터 셀 선택, 하이라이트, 기본 툴 상태 머신
- 64x64 디버그 그리드

### 테스트

- 좌표 왕복, 경계, 청크 계산 EditMode 테스트
- 다른 화면 비율에서 선택 정확도 PlayMode 테스트

### 완료 조건

- 사용자가 모든 셀을 정확히 선택할 수 있다.
- 카메라 조작이 셀 선택과 충돌하지 않는다.
- 그리드 데이터는 MonoBehaviour 없이 테스트 가능하다.

## 5. Phase 2 — 도로, 구역, 필지

### 산출물

- 직선 드래그 도로 설치·철거와 비용 미리보기
- 도로 그래프 및 연결성 버전
- 지도 경계의 외부 도로 연결과 도달 가능성
- R/C/I 저밀도 구역 칠하기·해제
- 도로 접면을 기준으로 한 단순 필지 생성
- 도로/구역/필지 디버그 오버레이
- Command 실행과 undo가 아닌 취소 가능한 배치 미리보기

### 테스트

- 교차로, 막다른 길, 철거 후 연결성
- 구역 중첩 및 도로 위 구역 금지
- 필지 도로 접근성 판정
- 고립 도로망과 외부 연결 도로망 판정

### 완료 조건

- 도로에 접하지 않은 구역은 개발 후보가 되지 않는다.
- 외부 연결에 도달할 수 없는 고립 도로망은 신규 이주·시장 접근을 만들지 않는다.
- 그래프 변경 시 버전과 Dirty 영역이 정확히 갱신된다.
- Placeholder 렌더러로 도로 연결 형태를 구분할 수 있다.

## 6. Phase 3 — 전력, RCI, 성장, 경제

이 Phase가 첫 플레이 가능한 MVP다.

### 산출물

- 발전소 배치와 연결 요소 기반 전력 공급
- 인구, 일자리, 점유율의 건물 단위 통계
- 집계 노동력·취업자·실업자·빈 일자리와 단순 고용 매칭
- 주택·일자리·외부 연결을 이용한 월별 집계 이주
- 한 종류의 집계 상품 공급·소비력·사업체 가동률
- 단순 RCI 수요와 월간 평활화
- 저밀도 R/C/I 각 3종 정의와 placeholder Prefab
- 개발 후보 샘플링, 건설 시간, 성장 제한
- 민간 도시경제와 분리된 세율, 건설비, 유지비, 시 재정 월간 원장
- HUD의 날짜, 재정, 인구, RCI 표시

### 최소 피드백 루프

```text
외부 연결 + 도로 + 구역 + 전력
  -> 주택/사업체 성장
  -> 이주 + 입주 + 고용
  -> 소비/상품 + 세금/유지비
  -> 실업/빈집/시장 기반 RCI 변화
  -> 추가 성장 또는 정체
```

### 완료 조건

- 도로·전력·수요 중 하나가 없으면 성장하지 않는다.
- 세율 변화가 다음 월부터 수요와 재정에 관찰 가능한 영향을 준다.
- 빈 일자리 증가가 주거 수요를, 실업 증가가 주거 수요 감소를 유발한다.
- 빈집·빈 점포·미충원 일자리가 누적되면 해당 용도의 추가 개발이 둔화된다.
- 같은 시드와 명령 기록으로 같은 월별 통계를 재현한다.
- 30분 동안 치명적 오류 없이 플레이 가능하다.

## 7. Phase 4 — 저장과 복원

### 산출물

- 버전이 있는 전체 도시 스냅샷
- 저장/불러오기 UI와 자동 저장의 원자적 교체
- ScriptableObject definition ID 검증
- 저장 마이그레이션 테스트 골격
- 명령 기록 또는 테스트 fixture를 이용한 결정성 회귀 테스트
- RNG 상태, 현재 tick/sequence, 시스템별 다음 실행 시점 저장

### 완료 조건

- 성장 중인 도시를 저장하고 재실행 후 동일 상태로 복원한다.
- 화면용 차량, View instance, 캐시가 저장 데이터에 포함되지 않는다.
- 손상 파일과 알 수 없는 버전을 사용자에게 안전하게 알린다.

## 8. Phase 5 — 집계 교통

### 산출물

- 고용 매칭과 시장 흐름에서 건물/청크 단위 출발지-목적지 통행 생성
- 목적지 매칭과 대표 경로 1~3개
- 경로 캐시와 도로 버전 기반 무효화
- 용량 대비 교통량, 유효 속도, 평균 통근시간
- 실제 통행량을 샘플링한 pooled 차량
- 혼잡 데이터맵

### 완료 조건

- 병목 도로가 통근시간과 주거 선호도에 영향을 준다.
- 표시 차량을 0대로 해도 시뮬레이션 결과가 동일하다.
- 128x128 벤치마크에서 틱 예산을 기록한다.

## 9. Phase 6 — 입지와 쇠퇴

### 산출물

- 토지가치, 오염, 소음, 범죄의 청크/셀 필드
- 공원 효과
- 용도별 선호도 가중치
- 점유율 감소, 상태 악화, 폐건물, 재개발
- 문제 원인 툴팁과 데이터맵

### 완료 조건

- 조건 악화에서 쇠퇴까지 시간 지연이 있다.
- 플레이어가 데이터맵과 건물 정보에서 원인을 확인할 수 있다.
- Dirty 영역 밖의 필드는 불필요하게 다시 계산되지 않는다.

## 10. Phase 7 — 서비스와 밀도

### 산출물

- 경찰, 소방, 학교, 병원, 폐기물의 범위·용량·예산
- 공원·환경의 공간 거리 필드와 출동 서비스의 도로 이동시간 필드 분리
- 사건 발생 시에만 생성되는 출동 차량
- 수도 시스템
- 중·고밀도 조건, 성장 CAP, 건물 업그레이드
- 서비스 예산 UI

### 완료 조건

- 서비스 부족과 예산 삭감이 단계적으로 도시 상태에 반영된다.
- 고밀도 개발은 인구, 수도, 입지, 도로 조건을 모두 요구한다.

## 11. Phase 8 — 규모와 성능

### 산출물

- 128x128 및 256x256 Benchmark fixture
- 건물/차량 View pooling, GPU instancing, LOD
- 경로와 데이터맵 프로파일 보고서
- 병목에 한정한 Jobs/Burst 도입
- 저장 크기와 로드 시간 최적화

### 완료 조건

- 128x128, 건물 2,000개, 표시 차량 500대에서 목표 프레임을 만족한다.
- GC Alloc, CPU/GPU frame time, 틱 시간을 `Docs/Benchmarks`에 기록한다.
- 최적화 전후 결과가 숫자로 비교된다.

## 12. Phase 9 — 아트, UX, 출시 준비

### 산출물

- 일관된 로우폴리 건물·도로·환경 세트
- 텍스처 아틀라스, LOD, collider 검증
- 낮/밤, 사운드, 튜토리얼, 접근성 옵션
- 세이브 호환 정책과 릴리스 체크리스트
- Windows/macOS 빌드

### 완료 조건

- 신규 사용자가 설명 없이 도로→구역→전력→성장 루프를 수행한다.
- 주요 도시 문제는 화면, 데이터맵, UI 중 두 곳 이상에서 설명된다.
- 출시 후보 빌드가 두 대상 플랫폼에서 동일 저장을 열 수 있다.

## 13. 병렬 작업 스트림

기반 계약이 확정된 뒤 다음 작업은 서로 다른 브랜치에서 병렬 진행할 수 있다.

| 스트림 | 소유 영역 | 다른 스트림과의 계약 |
|---|---|---|
| Simulation | `Runtime/Core`, `Simulation`, `Application` | 안정 ID, Command, Query, Event |
| Construction | `Gameplay/Construction`, 도로·구역 View | 명령 DTO, 셀 좌표, 비용 결과 |
| Presentation | `Presentation`, 카메라, 오버레이 | Read model, 변경 집합 |
| UI/UX | `Runtime/UI`, UI content | Query, ViewModel, command facade |
| Art | `Content/Art`, Blender | 크기, pivot, material, prefab 규약 |
| Tooling/QA | `Editor`, `Tests`, `Tools`, CI | 생성 메뉴, fixture, benchmark 출력 |

한 사람이 여러 스트림을 맡더라도 한 브랜치에서는 하나의 수직 기능만 처리한다. Scene 파일은 담당자를 한 명으로 제한하고 생성 스크립트 변경을 우선한다.

## 14. 우선 백로그

Phase 0 이후 첫 이슈는 다음 크기로 나눈다.

1. `Core`: `CellCoord`, `ChunkCoord`, 안정 ID, tick/sequence, 결정적 RNG 구현 및 테스트
2. `Simulation`: 64x64 `WorldState` 초기화와 셀 조회 테스트
3. `Application`: 고정 스텝 `SimulationClock`, 도시 명령 queue, 별도 배속 control
4. `Simulation`: 지도 경계 `ExternalConnection`과 도로 도달성
5. `Gameplay`: 화면 ray에서 셀 좌표 선택
6. `Presentation`: 선택 셀 하이라이트와 디버그 그리드
7. `Editor`: Prototype Scene 필수 구조 생성·검증 메뉴
8. `QA`: Bootstrap/Prototype Scene smoke test

각 이슈는 가능하면 코드, 테스트, 검증 방법을 함께 포함하고 1~3일 안에 검토 가능한 크기로 유지한다.
